# TL-Verilog Core for RISC-V Tournament

A complete RV32I implementation in TL-Verilog for the RISC-V compliance tournament framework.

✅ **Status**: Working - Passes RISCOF compliance tests

This directory holds the resource-shared version: the ALU adder, the
jump/branch target adder, the late PC adder, and the comparison subtractor
are each shared across their users through operand muxes. The readable
variant without any sharing lives in `cores/tlverilog_unshared/`; the two
are functionally equivalent, and either directory can be deleted on its own.

## Implementation Details

- **HDL**: TL-Verilog (compiled to SystemVerilog using sandpiper-saas)
- **Architecture**: 3-stage pipeline (@0-@3) based on MYTH workshop patterns
- **ISA**: RV32I (40+ instructions)
- **Simulator**: Icarus Verilog
- **Flip-Flops**: 82 generated by SandPiper
- **Performance**: ~9 second builds, ~1-2 seconds per test

## Build Flow

The Makefile integrates `sandpiper-saas` to compile TL-Verilog to SystemVerilog:

1. **TL-Verilog Source**: `rtl/rv32i_plh.tlv`
2. **Compilation**: `sandpiper-saas --reset0` generates:
   - `build/gen/rv32i_plh.v` (main core logic)
   - `build/gen/rv32i_plh_gen.v` (pipeline registers)
3. **Support Modules**: 
   - `register_file.v` from reference (inverted clock)
   - `instruction_memory_fast.v` and `data_memory_fast.v` (optimized for simulation)
   - `clk_gate.v` (SandPiper helper)
4. **Simulation**: Icarus Verilog with `-g2005-sv` flag
5. **Verification**: RISCOF compliance test framework

## Dependencies

- `sandpiper-saas` - TL-Verilog compiler at `~/.local/bin/sandpiper-saas`
- RISC-V toolchain - `riscv32-unknown-elf-gcc` and related tools

## Usage

```bash

# Debug with VCD waveform
make sim DEBUG_VCD=1

vvp sim.vvp +debug

```

## Architecture

**Pipeline Stages**:
- @0: PC calculation and reset handling
- @1: Instruction fetch and decode
- @2: Register read with bypass forwarding
- @3: Execute, memory access, writeback

**Memory Map**:
- `0x00000000` - Instruction memory (IMEM)
- `0x10000000` - Data memory (DMEM)  
- `0x20000000` - GPIO outputs (LEDs)

## Memory Modules

**Optimized for Simulation**:
- `instruction_memory_fast.v` - Direct array assignment (~100x faster)
- `data_memory_fast.v` - Direct array assignment (~100x faster)

**Reused from Reference**:
- `register_file.v` - Uses inverted clock for read-during-write
- `gpio_mem.v` - GPIO/LED peripheral

**Helper Modules**:
- `clk_gate.v` - SandPiper clock gating primitive

## Debugging

The enhanced testbench provides:
- Cycle counter and instruction counter
- PC tracking and timeout detection
- VCD waveform generation
- Register file dump on completion/error
- ECALL signature export

Enable debugging with:
```bash
make sim DEBUG_VCD=1
```

## Known Issues & Workarounds

1. **ECALL Timing**: Register file uses inverted clock, so testbench waits `@(posedge clk)` after ECALL detection
2. **Reset for Synthesis**: Internal reset is simulation-only; external reset needed for FPGA
3. **Reference Model**: Sail simulator not installed (prevents RISCOF signature comparison)

## Implementation Notes

- Uses MYTH workshop pipeline patterns (@0-@3 stages)
- TL-Verilog `>>N` syntax refers to N cycles in the PAST, not future
- SandPiper generates 82 flip-flops automatically
- `--reset0` flag used for simulation builds to initialize flip-flops
